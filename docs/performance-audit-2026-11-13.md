# Xneon Launcher: аудит производительности — 13 ноября 2026

## Область и условия проверки

Проверены исходники renderer, Electrobun main, preload/RPC, SQLite, сканера контента,
наблюдателей файлов, startup, навигации, тем, изображений и production-бандла.
Изменения внесены поверх текущей рабочей копии, а не сравнением с Electron HEAD:
в копии уже присутствовали пользовательские изменения, которые не откатывались.

Среда: Windows 11 x64, Bun 1.4.4, React 19.2.8, Electrobun 2.0.6, WebView2.
Клиентская ширина окна 1280. Основной профиль использован только для обычного
запуска/чтения. Массовая проверка SQLite выполнялась на синтетических данных
в отдельной БД `:memory:`: 50 сборок × 1000 модов.

Chrome DevTools MCP недоступен. Использован прямой локальный CDP WebView2:
PerformanceObserver, Runtime, Network, HeapProfiler и реальные события renderer.
Новые зависимости и внешние сканеры не устанавливались. Исходники и профиль
не отправлялись стороннему сервису аудита.

### Что именно измерялось

- **Process → interactive**: от создания `launcher.exe` до наличия интерфейса
  и удаления splash, три отдельных запуска процесса.
- **Renderer ready / reveal**: `app:hydrated` и `app:revealed` от начала документа.
- **Навигация**: клик по сайдбару → активная страница без видимой Suspense-заглушки
  → два кадра. Это готовность страницы, не завершение всех внешних HTTP-запросов.
- **IPC**: количество и длительность вызовов API. Аргументы, токены и ответы
  в журнал замеров не записываются.
- **Long Tasks**: задачи renderer длительностью от 50 мс за заданный маршрут.
- **JS heap**: отдельный повтор одинакового маршрута с принудительным GC CDP.
  Это не общий RSS приложения и не сумма процессов GPU/WebView2.
- **Бандл**: байты файлов и замыкание статических импортов. «Входной граф»
  не равен всему коду, который понадобится для полной главной страницы.

Холодный renderer-прогон выполнялся с отключённым HTTP-кэшем; два следующих —
с включённым. Холодный старт ОС после перезагрузки, чистый профиль и профиль
из тысяч реальных модпаков не измерялись. Такие показатели не заявляются.

## Подтверждённые проблемы и исправления

### P0: видимость готового интерфейса блокировалась декорацией

`src/startup-splash.ts` принудительно ожидал `2800 - elapsed`, затем 180 мс fade.
React уже был готов примерно через четверть секунды. Убрано минимальное ожидание;
fade 180 мс сохранён, при reduced-motion splash удаляется сразу. Никакие данные
не загружаются «быстрее» за счёт сокрытия ошибок или искусственного таймера.

### P1: тяжёлые библиотеки попадали в startup через manualChunks

Общий `vendor` и принудительные группы Radix/Markdown создавали общие зависимости,
через которые parse5/Markdown и Prism оказывались нужны входной точке.
Проверены четыре сборки: исходная, автоматическая, без общего vendor и целевая.
Выбрана целевая: отдельно React, Tabler и 3D; остальные границы определяет граф.
Полностью автоматический вариант создавал около 89 JS-чанков, включая множество
маленьких файлов иконок; он не выбран. Итоговый набор — около 75 чанков,
но критический входной граф уменьшен. Добавлен Vite manifest для контроля графа.

### P1: первый Suspense-переход задерживал показ на ~300 мс

Новый `lib/page-loader.ts` объединяет prefetch и открытие одним Promise и хранит
готовый модуль. `preloaded-page.tsx` рендерит уже готовый компонент напрямую:
одного предварительного `import()` было недостаточно, `React.lazy` всё равно
мог впервые приостановиться. Перед переключением ожидается готовность модуля,
старый интерфейс остаётся активен, обновление выполняется через transition.
Счётчик запросов не даёт позднему импорту отменить более новый выбор пользователя.

`page-loaders.ts` прогревает сборки/настройки/серверы последовательно в idle после
готовности главной, без их монтирования и без сетевых эффектов страниц. Остальные
модули предзагружаются по наведению или фокусу сайдбара. Нет таймера, маскирующего
задержку; если idle API отсутствует, остаются intent-prefetch и import по запросу.

### P1: навигация уничтожала состояние часто используемых страниц

Для сборок и настроек применён ограниченный `Activity visible/hidden`.
State сохраняется, скрытые эффекты снимаются React. При возврате допустима
повторная подписка/актуализация, но не потеря выбранного экрана и формы.
Отдельные счётчики root-reset больше не сбрасывают скрытую страницу другого раздела.
Обычный вход в настройки сохраняет внутреннюю вкладку, явная смена initialTab работает.

Проверено в WebView2: вкладка «О приложении» и карточка сборки переживают переход
в аккаунты и обратно; повторный клик по сайдбару возвращает список сборок.
Главная не удерживается: её одноразовые команды Play/CLI по-прежнему обрабатываются
при открытии. GPU-страницы, агент и облако не оставлены постоянно смонтированными.

### P1: настройки создавали 19 независимых сериализаций RPC

Добавлен ограниченный `settings:get-many` / `getSettings(keys)`, использующий уже
имеющийся кэш настроек main. Обновлены handler, preload, общий контракт и каталог
агента. Приватные AI-ключи исключены точно так же, как при индивидуальном чтении;
максимум 128 ключей, дубликаты объединяются. Профили/токены не передаются.

### P1: дублирование владельцев реестра тем

Launcher и SettingsPage независимо создавали одинаковые подписки, читали локальные
темы и применяли CSS. `ThemeRegistryProvider` теперь один, над приложением.
Используется snapshot, уже полученный `initializeTheme`, и дальнейшие push-события.
Нет нового дублирующего бессрочного кэша: сохранения, изменения из main и файловые
события продолжают синхронизацию. Стартовые чтения local themes: 3 → 1.

### P1: локальные серверы ожидали внешний сервис

`remote-servers/handlers.ts` дополнял локальный результат через `await listRemote()`;
`listRemoteServers()` при каждом запросе ожидал HTTP `/remote-servers`.
Теперь scoped snapshot возвращается без ожидания сети, обновление выполняется
фоном с TTL 30 с и объединением inflight-запросов. Найденные серверы приходят
через существующее `mc-server:remote-connection`. Ответы старого аккаунта/запроса
игнорируются, выход из аккаунта очищает snapshot. Добавлены тесты этих границ.

`useMcServers` получил тот же принцип, что у `use-builds`: локальный модульный
snapshot, показ без спиннера при возврате, TTL 3 с, обновление после действий/
импорта. Создание/удаление/правки сразу обновляют snapshot. Удалённый доступ не
сохраняется в renderer-кэше между монтированиями; он перечитывается с проверкой
текущего пользователя. Форматы серверов и сборок остаются разными намеренно.

### P1: ошибки SWR приводили к пустым данным и гонкам

Второй потребитель холодного ключа получал `undefined` вместо ожидания inflight.
Поздний ответ после invalidate мог перезаписать более свежий результат.
Исправлены ожидание, проверка поколения через идентичность entry, повтор после
null/ошибки и обработка синхронного исключения fetcher. TTL и persistent API сохранены.

### P2: 3D-движок загружался раньше потребности, скрытый viewer имел render loop

Статические импорты skinview3d удалены из общего кэша снимков; edit-модал и 3D-панель
грузятся по фактическому использованию. Сниматель один и теперь создаётся с
`renderPaused: true`, а не только `animation = null`: отсутствие анимации само
по себе не останавливало внутренний requestAnimationFrame skinview3d.
Проверена настоящая генерация PNG на локальной Steve-текстуре, дедупликация двух
запросов и последующее чтение результата из кэша (172 мс на этой машине).

### P2: бесполезный опрос запуска игры для неподвижного фона

`useMediaPaused` опрашивал JVM каждые 2,5 с даже без видео/анимации.
Теперь эффект включён только для video/particles/halo; статичная картинка не
создаёт таймер. В проверке простоя 5,5 с таких запросов было 0.

### P2: квадратичное сопоставление списка сборок

При reload каждый build искал предыдущее состояние через `find` по всему списку.
Заменено двумя Map по id/имени. Никакое новое memo всего дерева не добавлено;
сохранены наложение несохранённых правок и кэш состава.

### Функциональная правка по ходу аудита: внешние ссылки

Native notifications о навигации не являются отменой DOM-клика WebView2.
Добавлен renderer-перехват обычных/средних кликов и `window.open`: разрешённые
HTTP(S)/mailto адреса отменяют навигацию и уходят в `openExternal`.
Собственные views/якоря не перехватываются, обработанный приложением клик не
дублируется. Переходы внутри специально открытой читалки новостей не менялись.
Тест на DOM WebView2 проверил клики по вложенному SVG, target=_blank, средний клик
и сохранение адреса `views://launcher/index.html`. Внешний браузер в автоматической
проверке не открывался: использован подставной callback того же обработчика.

## Стратегия загрузки страниц

| Класс | Страницы | Подход |
| --- | --- | --- |
| Critical | shell, главная, язык, стартовая тема | Немедленно; после готовности убирается splash |
| Frequently Used | сборки, настройки, серверы | Idle/intent-prefetch; сборки и настройки сохраняют state через Activity |
| Rarely Used | аккаунты, статистика, логи | Intent-prefetch + загрузка по запросу |
| Heavy | агент, облако, скины, детали/Markdown/3D | Отдельные модули; без keep-alive GPU и фоновых сетевых задач |

Сравнение вариантов: обычное условное монтирование экономит RAM, но теряет state;
lazy экономит startup, но без prefetch даёт первый waterfall; prefetch сам по себе
не сохраняет состояние; постоянное CSS-скрытие всех страниц оставляет фоновые
таймеры, observers и WebGL. Выбран смешанный вариант с пределом две Activity-страницы.

## Что проверено и намеренно не переписано

- SQLite — уже `bun:sqlite`, WAL/NORMAL, подготовленные выражения (лимит 200),
  кэш настроек, индексы createdAt/startedAt/sourceId. UI имеет отдельный WebView-поток.
  Перенос соединения в worker/новый процесс измерениями не оправдан.
- Бенчмарк настоящих функций `loadBuildsLight`/`loadBuilds`: **0,22 мс / 25,32 мс**
  с mapping+JSON serialization, **14 831 / 6 101 331 байт**. EXPLAIN подтверждает
  `idx_builds_createdAt`. Этот существующий лёгкий путь сохранён, SQL-схема не менялась.
- Инстансы уже загружают контент только выбранной сборки, используют watcher-token
  и обновляют отдельную сборку. Установленные моды уже разбиты на страницы;
  дополнительная библиотека виртуализации здесь не нужна без нового профиля.
- Сканер/резолвер используют файловые метаданные и workers. Не заменялись на
  синхронное чтение и не распараллеливались без ограничений.
- LaunchLogsContext уже отделяет state логов от controls и батчит строки;
  глобальный React store не заменён ради смены технологии.
- Совместимые обёртки desktop/ipc-router, fork Minecraft worker, локальный HTTP
  asset server и sandbox читалки имеют реальные функции. Доказательств, что их
  удаление даст выигрыш, нет; они сохранены.
- Electron-подобная заставка с обязательным временем и ручное объединение тяжёлых
  vendor-библиотек оказались избыточны. Сходство API само по себе не причина удаления.
- Новых npm-зависимостей нет; содержимое формы/права доступа/экспорт/запуск сохранены.

## Остаточные риски и рекомендации

Это не утверждение, что найдены абсолютно все возможные узкие места.
Ниже — обнаруженные ограничения, которые не оправдывают рискованную перепись
без следующего измерения, а не скрытые незавершённые исправления этой задачи.

1. **Большие логи серверов**: `useMcServerLogs` хранит все строки сессии и копирует
   массив при push. При действительно длительных/high-volume сессиях нужно отдельно
   измерить UI и ввести chunk-buffer/windowing без потери поиска/экспорта логов.
2. **Открытие списка сборок/серверов с сотнями карточек**: текущий профиль мал,
   синтетический тест покрывает SQLite/JSON, а не рендер тысяч плиток. Виртуализацию
   плиток внедрять по результатам большого fixture-профиля, не вслепую.
3. **Startup migrations/quick_check/backup**: сохранены до startupReady ради
   целостности данных. Их время на многогигабайтной БД не измерено; убирать эти
   гарантии ради лучшего числа нельзя. Сервис удалённых серверов больше не блокирует
   выдачу локального списка, но фоновые подключения всё ещё зависят от сети.
4. **CSS и переводы**: CSS почти не уменьшился; RU+EN остаются на старте для
   корректного fallback. Оптимизация не должна возвращать raw translation keys.
5. **SWR**: stale обновляется при обращении, но не уведомляет каждого потребителя
   о background result. Бесконечное хранение в памяти текущего session manifest и
   лимит общего search-кэша требуют отдельного soak-теста длительной сессии.
6. **Платформы**: native-профиль выполнен только на Windows/WebView2. Linux CEF и
   macOS WKWebView проверены типами/платформенными unit-тестами, не живым UI.
7. **Метрики**: не выдаём paint-ready за полноценный INP/TTI или React Profiler
   commit duration; прямого production React Profiler здесь нет. RSS всех процессов,
   OS-cold после перезагрузки и сетевой cache-miss по всем провайдерам не измерены.
8. Предупреждение `import.meta` у CJS-тестовой сборки `resources.ts` существовало
   до оптимизаций и остаётся. Не маскируется отключением диагностики.
