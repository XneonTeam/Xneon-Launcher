# Установка и обновление модпаков

Текущая реализация: `electrobun/main/builds/modpack-install.ts`; прикладные потребители — сетевые импортеры Modrinth, CurseForge, FTB и локальные MRPACK/CurseForge в `builds/index.ts`. Публичные IPC-имена и структура результата импорта сохранены.

## Порядок операции

1. В выбранном каталоге инстанса создаётся `.xnlc-modpack/transaction/stage` на том же томе.
2. Загрузки, проверка опубликованных хешей/размеров и распаковка overrides выполняются только в staging. Работающая версия не очищается.
3. Составляется план пофайловой замены/удаления. Проверяются локальные пути, ссылки, коллизии и неизменность управляемых файлов.
4. До первой замены сохраняется write-ahead `journal.json`. Старые файлы перемещаются в резервные `*.old`, новые — на место. Полного копирования миров или установленной сборки нет.
5. Сканируется **конечный** каталог, поэтому возвращаемые пути `installedMods` не указывают на staging. Ошибка/отмена скана вызывает откат.
6. После проверки записывается committed marker, staging/backup удаляются. Следующий импорт, запуск Minecraft и копирование инстанса восстанавливают незавершённую файловую транзакцию.

У одного каталога один владелец установки. До применения и непосредственно перед ним проверяется, что эта сборка не запущена. Watcher не публикует промежуточное содержимое во время применения; обычное чтение состава через IPC получает явный отказ, а не частичный snapshot.

## Владение файлами

`managed.json` хранит пути и SHA-256 последней установленной версии. Удаляются только отсутствующие в новой версии **доказанно управляемые и неизменённые** файлы. Локальные дополнения и изменённые overrides сохраняются. Существующие миры, screenshots, logs, backups и игровые caches не перезаписываются установкой пака.

Выключенный файл `.disabled` не включается автоматически при обновлении того же пути. Снятые с пака выключенные файлы сохраняются. Соответствие разных имён файлов одному проекту не выводится по похожему названию: это не доказательство идентичности.

### Старые профили без manifest

Раньше состав файлов, принадлежащих модпаку, не сохранялся. Неизвестные существующие файлы не удаляются и не затираются. Совпадающий с новым паком байт-в-байт файл можно безопасно принять в управление; остальные локальные файлы сохраняются.

Следствие: первое обновление старого профиля может сохранить лишние JAR предыдущей версии. Автоматическое удаление по расширению/каталогу намеренно не используется: оно снова уничтожило бы пользовательские дополнения. Полная миграция ownership старых профилей требует достоверного предыдущего manifest либо отдельного подтверждённого решения владельца. Это остаточное ограничение, не «полностью решённый» A01.

## Проверка загрузок

- Modrinth: проверяются переданные `sha1` и/или `sha512`.
- FTB: проверяется опубликованный `sha1`.
- CurseForge: batch-клиент сохраняет опубликованный SHA-1 и уже доступный размер; установщик проверяет их при наличии. Если API не вернул метаданные и сработала прежняя download-URL fallback, криптографическая проверка этого файла не заявляется.
- Ошибка одной параллельной загрузки дожидается завершения остальных уже запущенных задач до очистки staging. Новая пачка после ошибки/отмены не начинается.

## Восстановление и границы гарантий

Журнал использует атомарную замену служебного JSON и операции rename на одном томе. Проверяется восстановление после аварийного завершения процесса. Это **не** гарантия полной устойчивости к отключению питания/повреждению файловой системы: отдельный fsync всех файлов/каталогов не заявляется.

Если после аварии пользователь изменил файл, который требуется откатить, восстановление отказывает, сохраняя журнал и backup, а не затирает новые данные. При таком конфликте нужно сохранить `.xnlc-modpack/transaction` и вручную сопоставить конфликтующий файл с резервной копией; удалять весь служебный каталог вслепую нельзя.

Журнал и manifest не экспортируются в ZIP/облако/Share и не принимаются из внешнего архива как доверенная история установки. Обычная локальная копия сначала восстанавливает исходный инстанс и затем сохраняет его manifest.

Файловая транзакция не объединена в одну распределённую транзакцию с последующей записью метаданных версии через renderer/SQLite. Это отдельная граница состояния builds (A05). Live CDN, полный игровой запуск, macOS/Linux и отказ накопителя требуют отдельной проверки.

## Целевые проверки

`tests/electrobun/modpack-update.test.ts` вызывает настоящие зарегистрированные импортеры с изолированными provider/DB/scan-портами и реальными файлами. `modpack-install.test.ts` проверяет применение, откат, отмену, legacy/custom-файлы, ссылки, владение, журнал, аварийное завершение процесса и исключение служебных данных из экспорта.

Результаты конкретных прогонов, сборки и повторных измерений находятся в `architecture-audit/REMEDIATION.md`; исторический аудит не переписывается задним числом.
