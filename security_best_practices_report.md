# Повторная проверка безопасности Xneon Launcher

Дата: 25 октября 2026 года. Проверена текущая рабочая копия, включая незакоммиченные изменения. Код приложения не изменялся.

## Результат

После повторной оценки подтверждённых уязвимостей высокой важности не установлено. Ниже перечислены недостатки защиты и один ограниченный сценарий срыва облачной авторизации. Первоначальная оценка завышала срочность: цепочка через SVG требует контроля официального API категорий Modrinth, недоступного обычному автору мода, либо другого способа выполнения JavaScript в renderer. Эксплуатация в работающем Electron не проводилась. Подмена ответа HTTPS требует компрометации источника, его инфраструктуры или доверенного канала, а не просто нахождения в одной сети.

Уточнённая модель угроз пользователя: хранение токенов в незашифрованной локальной БД принято сознательно. Самостоятельным дефектом это здесь не считается; минимизация секретов в renderer остаётся возможной дополнительной защитой. Шифрование БД не устраняет XSS, если bridge возвращает токены.

Приоритеты после пересмотра: проверка протоколов внешних ссылок и ограничение OAuth-сервера loopback — небольшие профилактические изменения; очистка SVG, защита webview и проверка отправителей IPC — усиление границ доверия. Высокая важность пунктов 1 и 2 отозвана. Для пункта 6 подтверждён кодовый сценарий отказа авторизации, но сетевая доступность порта зависит от окружения и не проверена.

Критические уязвимости с подтверждённой эксплуатацией не установлены. Проверка зависимостей не завершена: `pnpm audit --prod --json` вернул `fetch failed` (см. `security-audit-dependencies.json`). Это не подтверждение отсутствия известных уязвимостей.

## Усиление защиты: высокая важность не подтверждена

### 1. Неочищенный SVG из API вставляется как HTML — CWE-79

- Места: `packages/xnlc-mods/src/modrinth-client.ts:466`, `electron/main/mods.ts:283`, `components/launcher/instance/category-badge.tsx:29`, `components/launcher/instance/category-badge.tsx:91`. Аналогичные вставки `cat.icon` есть в диалогах категорий и панели каталога.
- Доказательство: `icon: cat.icon ?? ""` передаётся через IPC в renderer; затем `dangerouslySetInnerHTML` получает `icon`. Проверка `startsWith("<svg")` не удаляет обработчики событий и вложенный активный HTML. `inheritSvgColor` в `lib/utils.ts` меняет стиль, но не очищает содержимое.
- Последствия: при контроле ответа API обработчики событий внутри SVG способны выполнить JavaScript в renderer. Например, SVG может содержать `foreignObject` с HTML-элементом и обработчиком ошибки. Код сможет вызвать `window.electronAPI.loadAccounts()` и другие методы bridge. Отсутствие CSP усиливает риск.
- Исправление: единая очистка SVG проверенной библиотекой с ограниченным SVG-профилем во всех местах вставки либо отображение SVG через `img` без включения его DOM в документ. Запретить обработчики событий, `foreignObject`, активные URL и внешние ссылки ресурсов согласно выбранной политике.
- Ограничение: произвольный автор проекта Modrinth не обязательно управляет иконками категорий. Подтверждена небезопасная граница доверия API, а не возможность атаки любым пользователем каталога. Для окончательной проверки нужен безопасный тест подменённого ответа в Electron.

### 2. Недоверенные URI передаются системным обработчикам — CWE-20

- Места: `electron/main/window.ts:47–49`, `electron/main/system.ts:541`, `electron/preload.ts:297`.
- Доказательство: `shell.openExternal(url)` вызывается без разбора URL и списка разрешённых протоколов как в `setWindowOpenHandler`, так и в IPC. Ограничение HTTP(S) в `will-navigate` не распространяется на эти два пути.
- Последствия: ссылка из недоверенного содержимого либо XSS может запустить зарегистрированный системный обработчик URI. Конкретный эффект зависит от ОС и установленных приложений; произвольное выполнение команд этой проверкой не доказано.
- Исправление: единая функция в main, принимающая только явно разрешённые протоколы (обычно HTTPS/HTTP); остальные схемы разрешать отдельно для конкретных функций. Использовать её во всех обработчиках открытия ссылок.

## Дополнительные меры и ограниченные риски

### 3. Webview разрешён без проверки параметров в main

- Места: `electron/main/window.ts:33–39`, `components/launcher/news-reader-modal.tsx:348–352`, `index.html:3–7`.
- Доказательство: `sandbox: false`, `webviewTag: true`; обработчика `will-attach-webview` в исходниках нет, CSP также не найдена. У читалки используется постоянная сессия `persist:xneon-news`.
- Последствия: получив выполнение JavaScript в основном renderer, атакующий сможет создавать дополнительные webview и выбирать их параметры, включая опасные настройки Node/preload. Это потенциальное усиление XSS до доступа к ОС; готовая цепочка RCE здесь не воспроизводилась. Текущая страница новости сама по себе не получает автоматически API основного окна.
- Исправление: в `will-attach-webview` принудительно задавать `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, удалять непредусмотренный preload и проверять URL/partition. Добавить ограничение разрешений сессии, навигации и окон гостей. Включить sandbox основного renderer после проверки совместимости preload; добавить CSP с хешем стартового inline-скрипта или вынести его в файл.

### 4. Отправители привилегированных IPC не проверяются — CWE-862

- Места: `electron/main/ipc-router.ts:65–71`, `electron/main/system.ts:415–418`, `electron/main/system.ts:541–548`, `electron/main/auth.ts:167`.
- Доказательство: обработчики игнорируют `_event`; общий router также не проверяет `sender`/`senderFrame`. OAuth callback IPC принимает переданный URL без проверки соответствующего окна.
- Последствия: если недоверенный фрейм или другое окно получит возможность посылать IPC, main выполнит операции с полномочиями приложения. Само отсутствие проверки не даёт обычной веб-странице доступ к `ipcRenderer`; это дополнительная граница защиты, а не доказанный самостоятельный удалённый обход.
- Исправление: проверять конкретный `webContents`, основной фрейм и доверенный документ. OAuth callback принимать только от соответствующего authWindow. Сохранить отдельные правила для разных типов окон; валидировать аргументы во время выполнения.

### 5. Токены аккаунтов хранятся открыто и возвращаются в renderer — принятое решение

- Места: `electron/db/accounts.ts:68–69`, `electron/db/accounts.ts:112–113`, `electron/db/accounts.ts:135–138`, `electron/main/system.ts:415`, `electron/preload.ts:132`, `src/AccountsContext.tsx:34`.
- Доказательство: `accessToken` и `refreshToken` непосредственно записываются в SQLite, читаются без расшифровки и попадают в React-контекст. Шифрования аккаунтов в `electron/db` не найдено.
- Последствия: копия БД раскрывает токены; XSS в renderer может получить refresh-токены через разрешённый bridge. Для кражи файлов БД требуется отдельный доступ к данным пользователя. Шифрование не защищает от процесса, уже работающего с полномочиями того же пользователя.
- Исправление: шифровать секретные поля через `safeStorage` с миграцией существующих записей и обработкой недоступности защищённого хранилища. Возвращать renderer только публичные поля аккаунта; обновление токенов и авторизованные запросы выполнять в main по ID аккаунта. Одного шифрования на диске недостаточно для защиты от XSS.

### 6. OAuth loopback-сервер доступен через все интерфейсы — CWE-668

- Места: `electron/main/cloud/oauth-loopback.ts:64–84`, `electron/main/cloud/oauth-loopback.ts:90`.
- Доказательство: `server.listen(config.port, ...)` не указывает loopback-адрес; запрос с `code` принимается на любом пути, ошибка обмена завершает всю авторизацию через `finish`.
- Последствия: при доступности порта через firewall узел локальной сети может отправить неверный код и сорвать текущую авторизацию. PKCE уже применяется и ограничивает подмену успешного обмена; захват аккаунта не установлен.
- Исправление: слушать явно loopback, согласовать адрес с redirect URI, проверять путь и ожидаемое состояние запроса. Посторонние и некорректные запросы не должны завершать ожидающий OAuth-процесс. Сохранить PKCE.

## Проверенные защитные меры

- Главное окно уже использует `contextIsolation: true` и `nodeIntegration: false`.
- Описания и changelog в проверенных компонентах обрабатываются через `rehype-sanitize`.
- В импорте миров есть проверка попадания пути внутрь целевого каталога. В архиве тем ограничены имена ресурсов, размер и количество записей, проверяются SHA-256.
- Ключи AI уже защищаются `safeStorage`; для удалённых AI endpoint предусмотрен HTTPS, HTTP ограничен loopback.
- В XN Skins OAuth присутствуют `state` и PKCE. Наличие HTTP в localhost redirect URI само по себе не отмечалось как уязвимость.

## Объём и ограничения

Проведён статический просмотр Electron window/preload/IPC, React HTML/SVG-вставок, хранения аккаунтов, OAuth, импорта архивов и путей файлов, тем, запуска процессов, updater и конфигурации упаковки. Проверка не является исчерпывающим аудитом всех строк проекта. Не проводились атаки на внешние сервисы, чтение пользовательских секретов, проверка подписей готового дистрибутива или динамическая эксплуатация. Сборка не запускалась: исходники не менялись, успешная сборка не проверяет перечисленные свойства безопасности.

После согласованных изменений нужны адресные регрессионные проверки и `pnpm run build`. Шифрование локальной БД не входит в рекомендуемый обязательный объём с учётом уточнённой модели угроз.

Рекомендации по Electron сверены с [официальным руководством по безопасности](https://www.electronjs.org/docs/latest/tutorial/security), в частности с проверкой webview, sandbox, отправителей IPC и внешних URI.
